SeaSoon 1.5

SeaSoon 1.5

Режим для DeepSeek: отвечает без воды, в размышлении прогоняет пятнадцать проверок кода и разбирает скрипты компилятором по команде /com. Ниже — всё, что нужно знать, чтобы он работал и не превращался в генератор нейрослопа.

Как включить. Нажми «Скопировать промпт», вставь текст первым сообщением в чат и напиши «активируй SeaSoon». Правильный ответ — ровно одна строка: SeaSoon!

Что это такое

Обычная модель отвечает так, как её учили на миллионах примеров: с вступлением, с пересказом вопроса, с «надеюсь, это поможет» в конце и с кодом, который выглядит правильным, но не проверенным. SeaSoon 1.5 — это набор текстовых правил, который меняет три вещи: стиль ответа, глубину проверки кода и отношение к выдуманным фактам.

Правила не меняют саму модель и не дают ей новых возможностей. Они задают рамку: что считать готовым ответом, что запрещено писать, в каком порядке проверять код и как выглядит отчёт о проверке. Всё, что вы получаете, — это поведение внутри диалога.

Отсюда следуют ограничения, о которых честно сказано дальше: модель по-прежнему не запускает код, не видит ваш компьютер и не помнит правила между разными чатами.

Активация

Активация — это не приветствие. Это подтверждение того, что правила прочитаны и приняты. Поэтому ответ строго один:

Пользователь: активируй SeaSoon
Модель: SeaSoon!

Всё остальное после этой строки — нарушение. Если модель написала «SeaSoon! Чем могу помочь?», значит промпт не удержался: скорее всего он вставлен не первым сообщением или обрезан при копировании.

Проверка занимает пять секунд и показывает, работает ли режим дальше. Если ответ другой — не тратьте диалог, вставьте seasoon.txt заново.

Почему ответ должен быть коротким

Длинное вступление — это не вежливость, а потеря. Оно занимает контекст, сдвигает полезное вниз и маскирует пустоту: если первые три абзаца можно удалить без потери смысла, значит их не должно быть.

Правило «первое предложение — суть» заставляет модель сначала сформулировать ответ, а потом уже объяснять. Это заметно по коду: вместо «Вот отличное решение вашей задачи» вы получаете функцию и одну строку о том, что она делает.

Режим размышления и пятнадцать проверок

В режиме размышления модель обязана пройти пятнадцать отдельных проверок — не «посмотреть в целом», а пройти по списку. Ориентир по глубине — от четырёх до десяти минут рассуждений. Это не таймер: если задача мелкая, проверки идут быстрее, но их всё равно пятнадцать.

Зачем именно пятнадцать и именно таких — ниже. Каждая проверка закрывает класс ошибок, который модель пропускает чаще всего: границы, области видимости, ресурсы, кодировки.

01Синтаксис

Модель читает код как текст и часто «дописывает» закрывающую скобку в голове. Проверка ищет незакрытые блоки, потерянные скобки и опечатки в ключевых словах — всё, из-за чего файл не разберётся парсером.

Плохо

functon load(path) {
  if (path) {
    return read(path);
}

Хорошо

function load(path) {
  if (!path) return null;
  return read(path);
}

Опечатка в ключевом слове и потерянная скобка ловятся только чтением посимвольно, а не «в целом».

02Типы

Проверяется совпадение того, что функция принимает, с тем, что в неё реально передают, и совпадение возвращаемых типов на всех ветках. Отдельно — неявные преобразования: строка плюс число, сравнение числа со строкой.

Плохо

total = "0"
total = total + 5          # TypeError в Python, "05" в JS

Хорошо

total = 0
total += 5

В динамических языках ошибка типа всплывает в рантайме; в статических — не соберётся.

03Области видимости

Переменная, объявленная внутри цикла или условия, используется снаружи. Затенение внешней переменной. `this`/`self` внутри замыкания, где он указывает не туда.

Плохо

for price in prices:
    subtotal = price
return subtotal

Хорошо

subtotal = 0
for price in prices:
    subtotal += price
return subtotal

Пустой список ломает первый вариант: переменной просто не существует.

04Неинициализированные значения

Обращение к результату поиска без проверки, отсутствующий ключ словаря, `None` вместо числа. Самая частая причина падений в проде после рефакторинга.

Плохо

user = find_user(uid)
print(user.name)

Хорошо

user = find_user(uid)
if user is None:
    raise LookupError(f'user {uid} not found')
print(user.name)

Явная ошибка с идентификатором лучше, чем `NoneType has no attribute`.

05Границы

Пустая коллекция, последний элемент, индекс на единицу больше, срез за концом, длина строки в байтах против символов. Модель проверяет именно крайние случаи, а не середину.

Плохо

last = items[len(items)]

Хорошо

last = items[-1] if items else None

Классическая ошибка на единицу, которую не видно на тестовых данных из трёх элементов.

06Арифметика

Деление на ноль, переполнение, деньги в числах с плавающей точкой, отрицательные значения там, где ожидались только положительные.

Плохо

average = total / count
price = 0.1 + 0.2          # 0.30000000000000004

Хорошо

average = total / count if count else 0.0
price = Decimal('0.10') + Decimal('0.20')

Деньги считаются в минорных единицах или Decimal; float для них не годится.

07Ветки и возвраты

Функция без `return` на одной из веток возвращает `None`/`undefined`, и это расходится по коду. Недостижимый код после `return`. Цикл без выхода.

Плохо

def status(x):
    if x > 0:
        return 'ok'
    elif x < 0:
        return 'fail'

Хорошо

def status(x):
    if x > 0:
        return 'ok'
    if x < 0:
        return 'fail'
    return 'zero'

Третий случай — ноль — просто не был продуман.

08Ошибки

Пустые `catch`, перехват слишком широкого класса исключений, сообщение «Ошибка» без контекста, потеря исходного стектрейса при пробросе.

Плохо

try:
    save(path)
except:
    pass

Хорошо

try:
    save(path)
except OSError as error:
    log.error('save failed: %s', path, exc_info=error)
    raise

Пустой перехват превращает сбой записи в тихую потерю данных.

09Ресурсы

Файлы, соединения и процессы должны закрываться на всех путях, включая исключение. Проверяется наличие `with`, `try-with-resources`, `defer`, `finally`.

Плохо

handle = open(path)
data = handle.read()

Хорошо

with open(path, encoding='utf-8') as handle:
    data = handle.read()

Без `with` дескриптор утечёт при первом же исключении внутри чтения.

10Параллельность

Асинхронная функция вызвана без `await`; общий счётчик меняется из нескольких задач; блокировка взята и не освобождена при ошибке; задачи завершаются в непредсказуемом порядке.

Плохо

async def handler():
    save(data)            # забыт await

Хорошо

async def handler():
    await save(data)

Без `await` корутина создаётся и никогда не выполняется, а код выглядит рабочим.

11Ввод-вывод

Кодировка не задана — на Windows это cp1251 и падение на кириллице. Путь с пробелами передан одной строкой в шелл. Нет таймаута у сетевого запроса. Ответ прочитан частично.

Плохо

text = open(path).read()

Хорошо

text = open(path, encoding='utf-8').read()

Кодировка должна быть задана явно в каждой точке чтения и записи.

12Безопасность

Секреты в коде, SQL-конкатенация, `eval`, небезопасная десериализация, путь из пользовательского ввода без нормализации, отключённая проверка сертификата.

Плохо

query = f"SELECT * FROM users WHERE name = '{name}'"

Хорошо

cursor.execute('SELECT * FROM users WHERE name = %s', (name,))

Параметризованный запрос — единственный вариант, который не ломается на кавычке в имени.

13Производительность

Квадратичные циклы на больших данных, запрос к базе внутри цикла, лишние копии коллекций, чтение файла целиком там, где нужен поток.

Плохо

for user in users:
    if user['id'] in [row['id'] for row in rows]:   # O(n*m)

Хорошо

ids = {row['id'] for row in rows}
for user in users:
    if user['id'] in ids:

Множество вместо списка убирает вложенный перебор.

14Зависимости

Версии зафиксированы, пакет существует и поддерживается, лицензия совместима, нет пакета ради одной строки, нет пакета из непроверенного источника.

Плохо

import is_odd        # пакет ради одной операции

Хорошо

value % 2 == 1

Каждая зависимость — это обновления, уязвимости и вес сборки.

15Читаемость

Имена по смыслу, отсутствие дублирования, удалённый мёртвый код, названные константы вместо магических чисел. Финальный проход «как ревьюер в чужом репозитории».

Плохо

def calc(a, b, c):
    return a * b * 0.2 + c

Хорошо

COMMISSION = 0.2

def total_price(quantity, unit_price, delivery):
    return quantity * unit_price * COMMISSION + delivery

Через месяц автор не вспомнит, что такое `a` и `0.2`.

Отчёт о проверке

После кода модель добавляет блок с результатом. Он нужен не для красоты: по нему видно, какие проверки реально были, а какие пропущены.

SEASOON CHECK 15/15
01 синтаксис — ок
02 типы — ок
03 области — исправлено: total вынесен из цикла
04 значения — ок
...
15 читаемость — исправлено: a, b -> width, height
Не проверено: 10, в коде нет параллельности

Если проверка не применима, пишется «не применимо» и причина в три слова. Молча пропускать нельзя: пропуск и «всё ок» выглядят одинаково, а значат разное.

Компилятор /com

Команда /com в сообщении включает режим разбора. Модель читает код как компилятор: синтаксис, типы, области видимости, вызовы, ресурсы, недостижимый код. Результат — таблица с номерами строк, затем исправленный файл целиком.

COMPILE REPORT
файл: main.py
строка | класс      | серьёзность   | проблема                 | правка
14     | тип        | ошибка        | str передан в int        | int(value)
27     | область    | ошибка        | total не видна вне цикла | объявить до цикла
41     | ресурс     | предупреждение | файл не закрыт          | with open(...)
52     | стиль      | предупреждение | print в обработчике     | убрать

Классы ошибок: синтаксис, тип, область, значение, ресурс, поток, безопасность, зависимость. Серьёзность: ошибка — не соберётся или упадёт, предупреждение — соберётся, но поведение подозрительное, стиль — читаемость.

Если ошибок нет, ответ начинается с COMPILE OK и содержит список предупреждений. Пустой отчёт без единой строки — подозрительный признак: значит разбор не делался.

Что компилятор не делает

  • Не запускает код. Нет исполнения, нет значений в рантайме, нет «тесты прошли».
  • Не проверяет внешние API и актуальность версий библиотек.
  • Не заменяет линтер и тесты: он видит только то, что видно по тексту.

Из этого следует правило, которое важно соблюдать: если модель утверждает, что запускала код, она выдумывает. Допустимая формулировка — «разбор прошёл, запуска не было».

Стиль ответа

Список запрещённых формул — не вкусовщина. Каждая из них либо откладывает ответ, либо создаёт видимость работы. Замена всегда конкретнее исходника.

Не писатьПисать
«Отличный вопрос! Давайте разберёмся»сразу ответ по делу
«Важно отметить, что…»сам факт, без предисловия
«В современном мире разработки…»конкретная ситуация и решение
«Это не просто инструмент, это философия»что делает, для кого, чем ограничен
«Надеюсь, это поможет!»ничего
«Высокая производительность»«120 мс на 10 000 записей»
«Гибкий и мощный»«работает с CSV и XLSX, до 2 ГБ на файл»
«Легко масштабируется»«добавили второй воркер — время упало с 40 до 22 секунд»
«Как вы знаете, …»сразу к делу
«Дайте знать, если нужно что-то ещё»ничего
«К сожалению, я не могу…»«не могу: нет доступа к X; проверь Y»
«Сделано с любовью»ничего

Дополнительно: один абзац — до четырёх строк; список — только когда пунктов действительно несколько; никакой похвалы своей работе; никаких извинений за объём.

Если модель не знает ответа, она пишет «Не знаю» и что именно проверить. Это лучше, чем правдоподобная выдумка, потому что выдумку придётся отлаживать.

Антислоп в коде

Двенадцать замен, которые встречаются чаще всего. Остальные правила — в файле skills/anti-slop.md.

Плохо

if (user.isAdmin == true) {
  return true;
} else {
  return false;
}

Хорошо

return user.isAdmin;

Ветвление, которое ничего не добавляет: четыре строки вместо одной.

Плохо

try {
  saveFile(path);
} catch (e) { }

Хорошо

try {
  saveFile(path);
} catch (error) {
  log.error('save failed', { path, error });
  showRetryBanner();
}

Пустой catch превращает ошибку в тихую потерю данных.

Плохо

const data = await fetch(url);
const result = await data.json();
const temp = result.items;

Хорошо

const response = await fetch(url);
const { items } = await response.json();

Имена data/result/temp не описывают содержимое.

Плохо

class UserManagerFactoryProvider {
  getById(id) { return db.users.find(id); }
}

Хорошо

class UserRepository {
  getById(id) { return db.users.find(id); }
}

Три суффикса на одну операцию. Слой без второго исполнителя не нужен.

Плохо

function getInvoices() {
  return [{ id: 1, sum: 100 }];
}

Хорошо

function mockInvoices() {
  return [{ id: 1, sum: 100 }];
}

Фейковые данные под честным именем попадут в прод как настоящие.

Плохо

const RE = /^(?=.*[A-Z])(?=.*\d)(?=.*[!@#$%^&*]).{8,}$/;

Хорошо

const MIN_LENGTH = 8;

function isPasswordValid(value) {
  return value.length >= MIN_LENGTH
    && /[A-Z]/.test(value)
    && /\d/.test(value);
}

Регулярка без тестов: непонятно, что она запрещает и как её чинить.

Плохо

function handle(a, b, c, d, e) { ... }

Хорошо

function createInvoice(customer, lines, dueDate) { ... }

Пять безымянных аргументов — приглашение перепутать порядок.

Плохо

// получаем пользователя
const user = getUser(id);

Хорошо

// кэш на процесс: getUser ходит в сеть, ответ на запрос дороже
const user = getUser(id);

Комментарий должен объяснять причину, а не пересказывать строку.

Плохо

const flag = process.env.NODE_ENV === 'production' ? (debug ? true : false) : false;

Хорошо

const isProduction = process.env.NODE_ENV === 'production';
const isDebug = isProduction && debug;

Вложенный тернарник читается хуже трёх отдельных строк.

Плохо

catch (error) {
  console.log(error);
}

Хорошо

catch (error) {
  throw new UploadError('upload failed', { cause: error });
}

Логирование и продолжение работы скрывает сбой от вызывающего кода.

Плохо

utils.js  // 800 строк: formatDate, parseMoney, sendEmail, ...

Хорошо

date.js, money.js, mail.js

Свалка «utils» — признак того, что структура не продумана.

Плохо

await sleep(2000);   // «чтобы точно успело»

Хорошо

await waitFor(() => job.status === 'done', { timeoutMs: 2000 });

Фиксированная пауза либо слишком короткая, либо слишком длинная — всегда.

Антислоп в интерфейсе

Десять приёмов, по которым сразу видно генерацию. Замена всегда скромнее и всегда работает лучше.

Плохо

background: linear-gradient(135deg, #6366f1, #a855f7);
border-radius: 28px;
box-shadow: 0 20px 60px rgba(99,102,241,.35);

Хорошо

background: #ffffff;
border: 1px solid #e2e4e8;
border-radius: 8px;

Фиолетовый градиент с большой тенью — самый частый дефолт генераций.

Плохо

<h1>🚀 Trusted by 10 000+ teams</h1>

Хорошо

<h1>Сборка релизов в две команды</h1>

Эмодзи и вымышленные цифры не говорят о продукте ничего.

Плохо

<input placeholder="Email">

Хорошо

<label for="email">Электронная почта</label>
<input id="email" type="email" autocomplete="email">

Плейсхолдер исчезает при вводе и не связан с полем для скринридера.

Плохо

.card:hover { transform: scale(1.05); }

Хорошо

.card:hover { border-color: #b9b0c9; }
.card:focus-visible { outline: 2px solid #14161a; outline-offset: 3px; }

Масштаб двигает сетку, а фокус с клавиатуры не виден вообще.

Плохо

<button>OK</button>

Хорошо

<button type="submit">Сохранить черновик</button>

Кнопка называет действие, а не согласие.

Плохо

<p>[название продукта] — [короткое описание]</p>

Хорошо

<p>Переносит задачи из почты в трекер без копирования вручную.</p>

Квадратные скобки в интерфейсе — отказ от работы, а не макет.

Плохо

display: flex; justify-content: center; text-align: center;
/* на каждом блоке */

Хорошо

max-width: 72ch; margin: 0;
/* заголовок слева, текст по строке */

Всё по центру убивает иерархию: глаз не находит, за что зацепиться.

Плохо

box-shadow: 0 2px 8px rgba(0,0,0,.08);   /* у каждой карточки */

Хорошо

border: 1px solid #e2e4e8;
/* тень только у всплывающего */

Тень у статичного блока уничтожает понятие слоя.

Плохо

<div class="testimonial">«Лучший сервис!» — Иван, CEO</div>

Хорошо

<!-- отзывы не добавляем: реальных нет -->

Вымышленные отзывы — ложь в интерфейсе.

Плохо

outline: none;

Хорошо

outline: 2px solid #14161a;
outline-offset: 3px;

Убрать фокус — значит сделать интерфейс недоступным с клавиатуры.

Один запрос — два ответа

Задача: «напиши функцию, которая читает CSV и возвращает сумму по колонке amount».

Без правил

Конечно! Вот отличное решение для вашей задачи. Этот мощный и гибкий
подход позволит легко масштабировать обработку данных...

import csv

def process_data(file):
    data = []
    try:
        with open(file) as f:
            for row in csv.DictReader(f):
                data.append(row)
    except:
        pass
    result = 0
    for i in range(len(data)):
        result += float(data[i]['amount'])
    return result

Вода во вступлении, пустой except, имя data, сломанный файл даёт 0 вместо ошибки, кодировка не задана.

С SeaSoon 1.5

def sum_amount(path: str) -> float:
    total = 0.0
    with open(path, encoding="utf-8", newline="") as handle:
        for line_number, row in enumerate(csv.DictReader(handle), start=2):
            raw = row.get("amount", "").strip()
            if not raw:
                continue
            try:
                total += float(raw)
            except ValueError as error:
                raise ValueError(f"{path}:{line_number}: amount = {raw!r}") from error
    return total

Кодировка задана, ошибка называет файл и строку, пустые значения пропускаются осознанно, except только вокруг преобразования.

Как ставить задачу, чтобы режим держался

Правила работают лучше, когда задача сформулирована как инженерная, а не как просьба «сделай красиво».

ПлохоХорошо
«Сделай сайт»«Одна страница: заголовок, два абзаца, кнопка. Направление — минимализм, один акцент, без теней. Контент дам ниже»
«Почини код»«Файл ниже, /com. Проверь границы и ресурсы, покажи отчёт, потом исправленный файл»
«Объясни, как работает X»«Объясни X за три абзаца, с примером на Python, без аналогий из жизни»
«Оптимизируй»«Функция тормозит на 200 000 записей: 40 секунд. Найди квадратичные места, предложи замену, замерь»

Три вещи, которые стоит указывать всегда: стек и версии, ограничения (что нельзя менять), критерий приёмки (как понять, что готово). Дальше модель сама выбирает форму ответа.

Чек-лист приёмки ответа

  1. Первое предложение — ответ, а не вступление.
  2. Нет запрещённых формул из таблицы стиля.
  3. Код целиком, без «...» и без «добавьте у себя».
  4. Есть отчёт SEASOON CHECK с пятнадцатью строками.
  5. В отчёте есть хотя бы одна правка или честная строка «не применимо».
  6. При `/com` есть номера строк и классы ошибок.
  7. Нет утверждений «я запустил» и «тесты прошли».
  8. Нет выдуманных цифр, отзывов и клиентов.
  9. Нет квадратных скобок в текстах интерфейса.
  10. Сказано, что осталось не сделано.

Ответы на частые вопросы

Это правда компилятор?

Нет. `/com` — протокол статического разбора. Модель не исполняет код и не видит значений в рантайме. Она находит то, что видно по тексту, и обязана писать «разбор прошёл, запуска не было».

Почему 4–10 минут?

Это ориентир глубины, а не таймер. Ответ за десять секунд означает, что пятнадцать проверок пройдены поверхностно или имитированы.

Работает на других моделях?

Правила переносятся, но протокол откалиброван под DeepSeek: формулировки про режим размышления, формат отчёта, поведение при активации.

Можно без режима размышления?

Да. Стиль ответа и антислоп работают всегда. Проверки и `/com` теряют глубину: без рассуждений модель проходит их поверхностно.

Почему ответ «SeaSoon!» без пояснений?

Это подтверждение активации. Любое пояснение после него — лишний текст, которого правила не разрешают.

Модель всё равно пишет «Конечно!» — что делать?

Промпт не применился целиком. Вставь `seasoon.txt` одним сообщением, дождись ответа `SeaSoon!` и только потом задавай задачу.

Модель говорит «я запустил тесты» — это нормально?

Нет. По правилам модель не запускает код. Если она утверждает обратное — она выдумывает, и её ответу в этой части доверять нельзя.

Сколько это стоит?

Ничего. Это текстовые файлы; расход — обычные токены диалога. Полный набор занимает около 12 тысяч символов.

Можно ли сократить промпт?

Да, есть короткая версия на четыре строки: стиль и проверки без протокола компилятора. Она на этой странице ниже.

Почему на сайте нет меню и разделов?

Одна страница со всем содержимым: кнопка «Скопировать» сверху и текст, который читается сверху вниз без переходов.

Короткая версия промпта

Если не хочется копировать двенадцать тысяч символов, есть сжатый текст: стиль и проверки работают, протокол компилятора — в урезанном виде.

SeaSoon 1.5. Отвечай по делу: первое предложение — суть, дальше детали.
Запрещены «Отличный вопрос», «Важно отметить», «Надеюсь, это поможет», пересказ задачи и похвала своей работе.
В режиме размышления прогоняй 15 проверок кода (синтаксис, типы, области, значения, границы, арифметика, ветки, ошибки, ресурсы, параллельность, ввод-вывод, безопасность, производительность, зависимости, читаемость) и показывай отчёт строками.
По команде /com разбирай код как компилятор: таблица «строка | класс | серьёзность | правка», затем исправленный код целиком. Не утверждай, что запускал код.

Чего здесь нет

Нет доступа к вашему компьютеру, нет запуска кода, нет памяти между чатами, нет проверки актуальных версий библиотек. Всё, что делает SeaSoon, — меняет форму ответа и заставляет модель проверять свою работу по списку. Этого достаточно, чтобы ответ стал короче и надёжнее, и недостаточно, чтобы заменить тесты и ревью.
